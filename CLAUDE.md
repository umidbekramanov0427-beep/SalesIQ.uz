# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SalesIQ (salesiq.uz) is a multi-tenant sales CRM + AI call-analytics SaaS for Uzbek sales teams. Read `AGENTS.md` too: this repo is connected to Lovable, so **never rewrite pushed history** (no force push, no amend/rebase/squash of pushed commits) and keep the pushed branch building.

## Working with the owner

- Reply to the owner in **Uzbek**. Code, comments and commit messages stay in English.
- Never print secrets (`/opt/salesiq/.env.server`, `/opt/supabase/.env`, tokens, passwords) — show only variable names or lengths. Ask before anything hard to undo (restarts of the database stack, DNS, deleting data).
- Database changes (owner-approved workflow): production is the **self-hosted Supabase on the VPS** (see "Production server" below). Show the owner the **complete SQL** and get an explicit "yes" for that migration; statements that delete or rewrite data need their own confirmation. Then apply it over SSH: `ssh root@185.191.141.144 'docker exec -i supabase-db psql -U supabase_admin -d postgres -X -v ON_ERROR_STOP=1' < supabase/migrations/<file>.sql`, and verify the same way with read-only queries (the new objects exist, `cron.job` is as expected, no errors). Read-only queries need no approval. The Supabase connector and the cloud project `tmqcycijexihpoflkcpu` are **not production** (paused since 2026-10-27) — never apply migrations there. Without SSH access, give the complete SQL in the reply (not just a file name) for the owner to run. If an earlier migration turns out to be wrong, ship a new idempotent fix migration as well — it may already have been run.
- Deploys: GitHub `main` → the VPS. `salesiq-autodeploy.timer` checks `main` every 5 minutes and runs `/opt/salesiq/deploy.sh` (pull, `npm ci`, build, restart, `/health`). After pushing, check it went live: `ssh root@185.191.141.144 'journalctl -u salesiq-autodeploy --since -15min --no-pager | tail; curl -s 127.0.0.1:3000/health'`; on a failed build read that log and fix. The Vercel project (team `sales-os3`, project `salesiq.uz`) is paused and no longer serves the site. Lovable is not used for development.
- Usual flow: develop on the session's `claude/...` branch, push it, then fast-forward `main` to it when `main` is an ancestor (`git merge-base --is-ancestor origin/main HEAD && git push origin <branch>:main`).
- The owner judges work visually and dislikes shallow "reskins" — UI requests mean changing the actual inner cards/forms, verified with screenshots.

## Commands

```bash
npm run dev            # vite dev server on :8080
npm run build          # build (Nitro) — also regenerates src/routeTree.gen.ts; the server builds with NITRO_PRESET=node-server
npx tsc --noEmit       # type check (no tsc script; slow, give it a few minutes)
npm run lint           # eslint (includes prettier via eslint-plugin-prettier)
npx prettier --write <files>
npm test                     # unit tests (tests/unit, vitest via npx -- see scripts/test-unit.sh)
npm test -- plan-gating      # one test file by name
npm run test:db              # database rule tests (supabase/tests) on a throwaway local Postgres
npm run check                # unit tests + tsc + build (what CI runs); `npm run check -- <url>` also smoke-tests a running app
npm run smoke -- https://salesiq.uz   # read-only smoke test (scripts/smoke.mjs), also run by the Uptime workflow
```

vitest is deliberately **not** a dependency: `bun.lock` resolves from Lovable's private registry, so adding packages risks breaking the install; `scripts/test-unit.sh` fetches vitest with npx instead. Unit tests use vitest globals (no `import from "vitest"`). `test:db` applies `supabase/tests/stub-schema.sql` (a minimal stand-in, not the real schema) plus the migrations listed in `scripts/test-db.sh`, then runs each `*.test.sql` (plpgsql `assert`s inside `begin … rollback`); when a new migration adds DB rules, add it to that list and extend the stub as needed. For UI changes also render the page and screenshot it (Playwright/Chromium is preinstalled in cloud sessions).

Python worker (`services/ai-worker/`): `pip install -r requirements-dev.txt && pytest` (run from that folder).

## Architecture

**One TypeScript app is frontend and backend.** TanStack Start (React 19, TanStack Router/Query, Tailwind v4) built by Nitro (`vite.config.ts`); production runs it as one long-lived Node server (`node-server` preset), so there is no serverless time limit (the `maxDuration: 120` setting only applied on Vercel).

- `src/routes/*.tsx` are pages; `src/routes/*.ts` with `createFileRoute(path)({ server: { handlers: { POST/GET } } })` are API endpoints (webhooks, crons, integrations). File name dots map to URL slashes (`integrations.telephony.webhook.ts` → `/integrations/telephony/webhook`). `src/routes/README.md` has the routing conventions. `routeTree.gen.ts` is generated by the build/dev server — commit it when routes are added, never hand-edit it; a new route's `createFileRoute("/x")` fails tsc until it is regenerated.
- Company addresses: a company with `organizations.subdomain` works only on `<sub>.salesiq.uz`. `SubdomainGuard` (inside `AuthGate`) moves its signed-in people off salesiq.uz/www with their session in the URL fragment to `/auth/handoff` (`src/lib/subdomain-handoff.ts`), and on a company address shows anyone from another company where their own workspace is. The platform owner is never moved; localhost and preview URLs are untouched.
- `__root.tsx` holds the `AuthGate`: everything requires login except an explicit public list (`/login`, `/signup`, `/pricing`, `/f/*` web forms, `/tma/*` Telegram Mini App, and `/` while logged out, which renders `components/marketing/Landing.tsx`). Authenticated pages render inside `components/layout/AppShell.tsx`.
- Viewport: computers and tablets get a fixed `width=1366` layout; phones (touch screen, short side < 768px) get `width=device-width` (1:1, no scaling) and `<html class="phone">` — both written before first paint by `PHONE_BOOT_SCRIPT` in `__root.tsx`, not by `head()`. The owner wants the desktop layout untouched and a separate phone app layout where nothing scrolls sideways: on phones the sidebar is replaced by `components/layout/MobileNav.tsx` (app bar on top, tab bar at the bottom with "Menyu" opening the drawer), the lead card switches between Suhbat/Ma'lumot panes, and floating buttons sit above the tab bar. Style phones with the `phone:` Tailwind variant and the `html.phone` rules at the end of styles.css (`.phone-joined` turns a row of controls into one hairline-divided panel; `.phone-tabs` turns section tabs into one sideways-scrolling pill row; stat/catalog card grids merge into one panel; fields are 16px so iOS doesn't zoom) rather than changing the default/desktop classes. TMA pages keep their own `viewport` meta.

**Supabase is the data layer and much of the business logic.**

- Browser: `integrations/supabase/client.ts` (publishable key, RLS-enforced). Almost all data hooks live in `src/hooks/crm/*.ts` (one module per area: `core` has `makeResource(table)` — generic list/insert/update/delete hooks keyed by table name — and the resources built on it); `src/hooks/use-crm-data.ts` is a barrel that re-exports them all, so import from `@/hooks/use-crm-data`. Inside `src/hooks/crm/`, keep module-level code (outside function bodies) depending only on `core` — the modules import each other in cycles, which is only safe for references inside functions.
- Server: `integrations/supabase/client.server.ts` exports `supabaseAdmin` (service role, **bypasses RLS** — always filter by `organization_id` yourself). Only import it from `*.server.ts` files or server route handlers; the Vite plugin blocks server-only imports in client code.
- Server routes authenticate with `Authorization: Bearer <supabase JWT>` (client side: `apiFetch` in `src/lib/api.ts`), checked via helpers in `src/lib/auth.server.ts` (`requireSuperAdmin`, `requireOrgMember`, …). Machine callers use shared secrets in headers (`x-cron-secret` = `CRON_SECRET`, `x-worker-secret` = `WORKER_SECRET`, `MIGRATION_SECRET`).
- Tenancy: every row has `organization_id`; RLS uses `current_user_org_id()` / `current_user_role()`. Roles: `super_admin`, `rop` (head of sales), `sotuv_menejeri` (rep; `is_intern` = trainee), `platform_owner` (operates the platform across orgs, `/platform/*`).
- Many rules are enforced **in Postgres**, not in TS: triggers for "zapret zadacha" (task/note required before a stage move), per-funnel duplicate blocking, missed-call → call-back task, seat limits at login (`check_seat_login`). Server-side writes run with `auth.uid()` null, and several triggers intentionally skip those.
- Scheduled jobs are `pg_cron` entries calling `net.http_post` to app endpoints or SQL functions directly.
- Monitoring: `src/server.ts` hands every 5xx and slow person-facing request to `recordServerIssue` (`monitoring.server.ts`); browser crashes POST to `/errors/log`. Both write `error_logs` (Platforma → Xatoliklar, Telegram ping to platform owners) and forward to Sentry (org `salesiquz`, project `salesiq`) via `sentry.server.ts`, a dependency-free envelope POST enabled by the `SENTRY_DSN` env var — no `@sentry/*` package (bun.lock risk).
- Monitoring bot (`src/lib/ops/`): the platform owner's Telegram reports — the 09:00 Tashkent "platforma holati" report, alerts on critical problems (checked every 15 minutes, each sent once a day via `platform_ops_log`) and commands `/holat`, `/kompaniyalar`, `/integratsiyalar`, `/xatolar`, `/yordam`. The rules are pure (`health.ts`, unit-tested); facts are gathered in `health.server.ts`; both run from the 5-minute `/telegram/send-daily-report` cron. With `OPS_TELEGRAM_BOT_TOKEN` set, every owner message (also server-error, security and support alerts via `notifyPlatformOwners`) goes through that separate bot, answered at `/telegram/ops-webhook`; without it the shared bot carries them and answers the slash commands in owners' chats.
- Live support (`support_messages`, `src/lib/support*.ts`): the assistant's Operator tab ↔ the owner's Telegram (reply to answer) and `/platform/support`; answers reach the open chat via Realtime.
- Product analytics: `src/lib/analytics.ts` batches events straight to Amplitude's HTTP API (no SDK package, no Session Replay), keyed by `VITE_AMPLITUDE_API_KEY` in `.env` (public ingestion key). `AuthGate` sends a `Page Viewed` per navigation (ids collapsed to `:id`, platform owner excluded); only profile id, role, org id and plan identify a user — never names, contacts, leads or calls.
- Platform-owner controls: the visits report (`/platform/sessions`, one card per sign-in; `/platform/visit/$sessionId` timeline) reads `user_login_events` (one row per browser-tab session, plus `kind = 'failed_login'` attempts from `/account/login-failed`) and `user_session_events` (pages, failed mutations, blocked pages/features, batched by `src/lib/session-trail.ts` to `/account/session-events`), merged with `audit_logs`/`error_logs` in `src/lib/visits.server.ts`; rows older than 30 days are purged by pg_cron. Its other tabs come from `src/lib/platform-insights.server.ts` (`/platform/insights`): trial engagement score (`src/lib/trial-score.ts`, also the 09:00 Tashkent Telegram digest sent from the 5-minute `/telegram/send-daily-report` cron, deduped by `platform_digest_log`), customer path (sign-up → bot+phone → lead → integration → paid), online now (the tab's once-a-minute heartbeat) and per-company usage (`/platform/usage/$orgId`). Security alerts (failed-password bursts per IP, new country/city, one login on two devices) go to platform owners' Telegram from `src/lib/owner-alerts.server.ts` and into the timeline as `alert:*` actions; "Seansni yopish" deletes the visit's auth session (`platform_revoke_auth_sessions`) and the tab signs out on its next heartbeat. Important actions are trailed from `apiFetch` (`TRAILED_ACTIONS` in `src/lib/api.ts`) and the CSV/PDF exports; Excel files are written by `src/lib/xlsx-write.ts` (no dependency). A frozen company (`organizations.frozen_at`, set with `active = false`) sees a frozen screen everywhere; unfreezing credits the frozen days (`unfreezePatch`). `integration_pauses` lets the owner pause one integration of a company — sync, webhooks, call events, SMS and outgoing webhooks check `isIntegrationPaused` (`src/lib/integration-pauses.server.ts`).
- Realtime: `pbx_calls` is in the `supabase_realtime` publication (incoming-call pop-up).
- Web push + PWA: `public/manifest.webmanifest` and `public/sw.js` (push, notification click, offline page); `src/lib/push/push.server.ts` `sendPush(org, profileIds, msg)` is the one sender (web-push, VAPID_* env, per-kind opt-outs in `notification_preferences.push_*`), fired on new leads (`lead-intake.server.ts`), client Telegram messages, ringing incoming calls (`recordPbxCallEvent`), support answers and assigned tasks. Devices are saved server-side by `/notifications/push`.
- Taklif dasturi (referrals): `?ref=CODE` is remembered by the browser (`src/lib/referral.ts`), `signup.create` records it (+7 trial days); the invited company's first Payme/Click payment gives the inviter +30 days and partners (`referral_partners`, Platforma → Hamkorlar) their commission (`rewardReferral` from `reactivateOrgAfterPayment`). Client payments (`src/lib/lead-payments/`, separate from the platform's own subscription billing): a company saves its own Payme/Click cashbox at `/integrations/payments` (keys sealed in `org_payment_merchants`), managers send `/pay/<id>` links from the lead card (`lead_payment_links`), and the provider's callback to `/lead-payments/{payme,click}/<org id>` marks the link paid and moves the lead to the funnel's paid stage (`pickPaidStage`). A link can repeat monthly (`lead_payment_schedules`, `src/lib/lead-payments/recurring*.ts`): the 5-minute `/telegram/send-daily-report` cron makes and sends it to the client's Telegram/Instagram and reminds once after 3 days; the home page's "Yig'ilgan to'lovlar" card sums what was really paid. The same cron sends company owners (super admins with Telegram) a Monday 09:00 weekly report (`src/lib/weekly-report*.ts`, deduped in `platform_ops_log`). Subscription documents (invoice, act, bill for bank transfer) are `/billing/doc` (`billing_.doc.tsx`, data from `/billing/documents`), seller = `platform_settings.company_requisites`. Platforma → Daromad (`src/lib/revenue.ts`) has MRR/churn/LTV.
- Uptime: `/health` (app + DB, 200/503) is polled every 30 minutes by `.github/workflows/uptime.yml` (private repo: Actions minutes), which also runs `scripts/smoke.mjs` and alerts Telegram on state changes (down / degraded / back); `ci.yml` (tests, tsc, build) runs only on pull requests and by hand to save minutes. Repo secrets `UPTIME_TELEGRAM_BOT_TOKEN`, `UPTIME_TELEGRAM_CHAT_ID`; a manual run can send a test message. Public pages and `/api/pricing` send 60 s cache headers (`src/lib/public-cache.ts`); there is no CDN in front of the server, so they only help browsers. There is no staging copy, so never test destructive changes against salesiq.uz.

**Migrations.** `supabase/migrations/*.sql`, timestamp-named, written to be idempotent (`if not exists`, `create or replace`, `drop … if exists`) because they are re-run by hand. Signed-out visitors (`anon`) get no EXECUTE on `public` functions (default privileges revoked in `20261113000000_security_hardening.sql`); a new `security definer` function that only the server calls should also `revoke execute … from authenticated` and be granted to `service_role`, and every RLS policy pins `organization_id = current_user_org_id()` next to any role check (`profiles.organization_id` / `role = platform_owner` can only change server-side). When adding or changing one, also update `src/lib/generated-migrations.ts` (the files embedded as JSON strings, served by `/admin/run-migrations?secret=…`), and once the migration is applied regenerate `src/integrations/supabase/types.ts` from the live database through postgres-meta on the server: `ssh root@185.191.141.144 'K=$(grep ^SERVICE_ROLE_KEY= /opt/supabase/.env | cut -d= -f2-); curl -s -H "apikey: $K" -H "Authorization: Bearer $K" "http://127.0.0.1:8000/pg/generators/typescript?included_schemas=public"'` (keep the file's existing exports; without SSH, add new columns/tables/functions by hand). Client code that depends on a new column should degrade gracefully until the migration has run (several hooks return `null` on a "column/function missing" error).

**Production server.** Everything runs on one Eskiz VPS (`ssh root@185.191.141.144`, key-only login, fail2ban; Ubuntu 24.04, 2 vCPU, 3.8 GB RAM + 4 GB swap). The firewall allows only 22/80/443 — Docker publishes every database/API port on `127.0.0.1` only; keep it that way, because Docker ports bypass ufw.

- App: `/opt/salesiq` (checkout of `main`, settings in `.env.server`), `salesiq.service` → `node .output/server/index.mjs` on 127.0.0.1:3000.
- Supabase: Docker Compose in `/opt/supabase` (settings in `.env`; Google sign-in and `ENABLE_EMAIL_AUTOCONFIRM=true` live there — restart only `auth` after changing them: `docker compose up -d --no-deps auth`). Public API `https://api.salesiq.uz` → gateway 127.0.0.1:8000. Storage files are on disk in `volumes/storage`. No SMTP is configured yet, so auth emails (password reset) are not sent.
- Caddy (`/etc/caddy/Caddyfile`): `api.salesiq.uz` → 8000, everything else → 3000 with on-demand TLS approved by `/tls-allowed` (salesiq.uz, www, vps, api and company subdomains). The first visit to a new company subdomain waits a few seconds for its certificate.
- pg_cron calls the app at `private.app_config.app_base_url` (`https://vps.salesiq.uz`, a direct A record) with `x-cron-secret`. The Telegram webhook is `https://salesiq.uz/telegram/webhook`.
- Backups: `salesiq-backup.timer` (03:30 Tashkent) runs `/usr/local/sbin/salesiq-backup` — full `pg_dump`, the app schemas in restorable parts, storage files and config into `/var/backups/salesiq/<date>` (last 7 kept), then an rclone-crypt encrypted copy to Backblaze B2 (remote `offsite:`, `daily/<date>`, 30 days) checked with `rclone cryptcheck`. Last result: `/var/backups/salesiq/last-status`. Only the owner holds the encryption passphrase.
- Checks: `curl -s 127.0.0.1:3000/health`; `docker compose -f /opt/supabase/docker-compose.yml ps`; recent cron runs in `cron.job_run_details`. Many fresh SSH connections get dropped while bots hammer port 22 — reuse one connection (`ControlMaster`) and run long jobs with `setsid nohup`.

**Plans and access.** `src/lib/plan-gating.ts` is the single feature matrix (`start_iq` / `analyst_iq` / `master_iq`, `SEAT_LIMITS`, `planHasFeature`); `src/lib/org-access.ts` adds trial/expired phases. Gate UI with `<PlanGate feature=…>` / `CrmGate` and server routes with `featureLockReason`. Seat limits are mirrored in SQL (`check_seat_login`) — change both together.

**i18n.** `src/lib/i18n.tsx` holds `useI18n`/`t()`; the dictionaries are `i18n-en.ts` (main bundle, the fallback), `i18n-uz.ts` and `i18n-ru.ts` (lazy-loaded). Lookup falls back uz/ru → en → key. Add every new key to all three dictionaries. `t(key, vars)` only interpolates when vars are passed.

**UI primitives.** `src/components/layout/Primitives.tsx`: `PageHeader`, `SectionCard`, `StatCard`, `SettingRow(s)`, `IconTile`, `StatusChip`. Pass `icon` + `tone` (palette in `src/lib/tones.ts`, shared with the sidebar's per-item `tone` in `src/lib/nav.ts`) so a section has the same color everywhere. Admin pages wrap content in `<SettingsLayout variant="admin">`, which switches the primitives to the larger admin look. Colors are semantic tokens in `src/styles.css` (`bg-card`, `bg-surface`, `text-muted-foreground`, …; dark mode via `.dark`); the public landing uses its own `.lp` token set.

**Navigation and help.** The sidebar (`src/lib/nav.ts`) is deliberately short: Bosh sahifa (`/`, the dashboard with Reyting as a tab; reps get only the Reyting), Voronkalar, Audio, Lid tahlili, Nazorat, Sinfxona, Settings; the Admin panel opens from the user menu (gold item). Every admin setting is one card in `src/components/admin/AdminCatalog.tsx` that opens one page — no nested hubs; integrations each get `/integrations/<slug>` (`integrations.$slug.tsx`, cards in `components/integrations/IntegrationCards.tsx`) and each telephony provider `/admin/telephony?provider=<id>`. Integration cards show the service's real logo (official marks in `public/brand/`, otherwise the site's favicon); platform features get a coloured icon. Every page header shows a "Qo'llanma" button: guides are in `src/lib/help/articles.ts` (uz/ru/en) and pages map to them in `src/lib/help/paths.ts` — when adding a page or changing a flow, update its guide; the AI assistant (floating button, `AiAssistantFab`) answers from the same guides.

**Integrations** live in `src/lib/<name>/` with `*.server.ts` logic: amoCRM and Bitrix24 sync (leads from them carry `amocrm_id` / `bitrix24_deal_id` and are analytics-only — CRM rules skip them), telephony (`src/lib/telephony/`, one module per provider, all webhooks normalized into `pbx_calls` by `recordPbxCallEvent`), Telegram bot (`telegram.webhook.ts`, one shared bot via `TELEGRAM_BOT_TOKEN`), Instagram Direct (`src/lib/instagram/`: one Meta app via `INSTAGRAM_APP_ID`/`INSTAGRAM_APP_SECRET`/`INSTAGRAM_WEBHOOK_VERIFY_TOKEN`, each company connects its account by OAuth at `/integrations/instagram`, token sealed in `instagram_accounts`; `/integrations/instagram/webhook` turns a new sender into a lead and keeps the conversation in `lead_telegram_messages` with `channel = 'instagram'`, so the lead card shows both channels), Gemini for AI (`gemini.server.ts`; call analysis is `analyzeCallById` in `audio-analytics.analyze.ts`).

**Python.**

- `services/ai-worker/` — small FastAPI service (Railway) that drains the AI call-analysis queue by calling `/audio-analytics/analyze-one` one call at a time; analysis logic stays in TS. Claims via `amocrm_calls.analysis_started_at` keep it and the pg_cron tick from analysing a call twice.
- `backend-python/` — an older, unfinished FastAPI port of the TS backend (see its `PORT_STATUS.md`). Not in production: `apiFetch` only targets it when `VITE_API_BASE_URL` is set, and it is left empty. The owner decided not to migrate the backend to Python; don't extend this port unless asked.
