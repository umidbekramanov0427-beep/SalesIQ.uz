# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SalesIQ (salesiq.uz) is a multi-tenant sales CRM + AI call-analytics SaaS for Uzbek sales teams. Read `AGENTS.md` too: this repo is connected to Lovable, so **never rewrite pushed history** (no force push, no amend/rebase/squash of pushed commits) and keep the pushed branch building.

## Working with the owner

- Reply to the owner in **Uzbek**. Code, comments and commit messages stay in English.
- The owner applies SQL by hand in the Supabase SQL Editor. Whenever a change needs a migration, give the **complete SQL** in the reply (not just a file name). If an earlier migration turns out to be wrong, ship a new idempotent fix migration as well — it may already have been run.
- Deploys: GitHub `main` → Vercel. After pushing, remind the owner to check that the Vercel deploy is **Ready** (Redeploy if not). Lovable is not used for development.
- Usual flow: develop on the session's `claude/...` branch, push it, then fast-forward `main` to it when `main` is an ancestor (`git merge-base --is-ancestor origin/main HEAD && git push origin <branch>:main`).
- The owner judges work visually and dislikes shallow "reskins" — UI requests mean changing the actual inner cards/forms, verified with screenshots.

## Commands

```bash
npm run dev            # vite dev server on :8080
npm run build          # production build (Nitro, Vercel preset) — also regenerates src/routeTree.gen.ts
npx tsc --noEmit       # type check (no tsc script; slow, give it a few minutes)
npm run lint           # eslint (includes prettier via eslint-plugin-prettier)
npx prettier --write <files>
npm test                     # unit tests (tests/unit, vitest via npx -- see scripts/test-unit.sh)
npm test -- plan-gating      # one test file by name
npm run test:db              # database rule tests (supabase/tests) on a throwaway local Postgres
```

vitest is deliberately **not** a dependency: `bun.lock` resolves from Lovable's private registry, so adding packages risks breaking the Vercel install; `scripts/test-unit.sh` fetches vitest with npx instead. Unit tests use vitest globals (no `import from "vitest"`). `test:db` applies `supabase/tests/stub-schema.sql` (a minimal stand-in, not the real schema) plus the migrations listed in `scripts/test-db.sh`, then runs each `*.test.sql` (plpgsql `assert`s inside `begin … rollback`); when a new migration adds DB rules, add it to that list and extend the stub as needed. For UI changes also render the page and screenshot it (Playwright/Chromium is preinstalled in cloud sessions).

Python worker (`services/ai-worker/`): `pip install -r requirements-dev.txt && pytest` (run from that folder).

## Architecture

**One TypeScript app is frontend and backend.** TanStack Start (React 19, TanStack Router/Query, Tailwind v4) built by Nitro for Vercel serverless (`vite.config.ts`, `maxDuration: 120`).

- `src/routes/*.tsx` are pages; `src/routes/*.ts` with `createFileRoute(path)({ server: { handlers: { POST/GET } } })` are API endpoints (webhooks, crons, integrations). File name dots map to URL slashes (`integrations.telephony.webhook.ts` → `/integrations/telephony/webhook`). `src/routes/README.md` has the routing conventions. `routeTree.gen.ts` is generated by the build/dev server — commit it when routes are added, never hand-edit it; a new route's `createFileRoute("/x")` fails tsc until it is regenerated.
- `__root.tsx` holds the `AuthGate`: everything requires login except an explicit public list (`/login`, `/signup`, `/pricing`, `/f/*` web forms, `/tma/*` Telegram Mini App, and `/` while logged out, which renders `components/marketing/Landing.tsx`). Authenticated pages render inside `components/layout/AppShell.tsx`.
- Viewport is deliberately fixed at `width=1366` (desktop layout shrunk on phones, owner's choice). Pages that must be mobile (TMA) override the `viewport` meta in their own `head()`.

**Supabase is the data layer and much of the business logic.**

- Browser: `integrations/supabase/client.ts` (publishable key, RLS-enforced). Almost all data hooks live in `src/hooks/use-crm-data.ts`; `makeResource(table)` gives generic list/insert/update/delete hooks keyed by table name.
- Server: `integrations/supabase/client.server.ts` exports `supabaseAdmin` (service role, **bypasses RLS** — always filter by `organization_id` yourself). Only import it from `*.server.ts` files or server route handlers; the Vite plugin blocks server-only imports in client code.
- Server routes authenticate with `Authorization: Bearer <supabase JWT>` (client side: `apiFetch` in `src/lib/api.ts`), checked via helpers in `src/lib/auth.server.ts` (`requireSuperAdmin`, `requireOrgMember`, …). Machine callers use shared secrets in headers (`x-cron-secret` = `CRON_SECRET`, `x-worker-secret` = `WORKER_SECRET`, `MIGRATION_SECRET`).
- Tenancy: every row has `organization_id`; RLS uses `current_user_org_id()` / `current_user_role()`. Roles: `super_admin`, `rop` (head of sales), `sotuv_menejeri` (rep; `is_intern` = trainee), `platform_owner` (operates the platform across orgs, `/platform/*`).
- Many rules are enforced **in Postgres**, not in TS: triggers for "zapret zadacha" (task/note required before a stage move), per-funnel duplicate blocking, missed-call → call-back task, seat limits at login (`check_seat_login`). Server-side writes run with `auth.uid()` null, and several triggers intentionally skip those.
- Scheduled jobs are `pg_cron` entries calling `net.http_post` to app endpoints or SQL functions directly.
- Realtime: `pbx_calls` is in the `supabase_realtime` publication (incoming-call pop-up).

**Migrations.** `supabase/migrations/*.sql`, timestamp-named, written to be idempotent (`if not exists`, `create or replace`, `drop … if exists`) because they are re-run by hand. When adding or changing one, also update `src/lib/generated-migrations.ts` (the files embedded as JSON strings, served by `/admin/run-migrations?secret=…`), and add any new columns/tables/functions to `src/integrations/supabase/types.ts` by hand (it is not regenerated here). Client code that depends on a new column should degrade gracefully until the migration has run (several hooks return `null` on a "column/function missing" error).

**Plans and access.** `src/lib/plan-gating.ts` is the single feature matrix (`start_iq` / `analyst_iq` / `master_iq`, `SEAT_LIMITS`, `planHasFeature`); `src/lib/org-access.ts` adds trial/expired phases. Gate UI with `<PlanGate feature=…>` / `CrmGate` and server routes with `featureLockReason`. Seat limits are mirrored in SQL (`check_seat_login`) — change both together.

**i18n.** `src/lib/i18n.tsx` holds the English dictionary and `t()`; `i18n-uz.ts` and `i18n-ru.ts` override it (lookup falls back uz/ru → en → key). Add every new key to all three files. `t(key, vars)` only interpolates when vars are passed.

**UI primitives.** `src/components/layout/Primitives.tsx`: `PageHeader`, `SectionCard`, `StatCard`, `SettingRow(s)`, `IconTile`, `StatusChip`. Pass `icon` + `tone` (palette in `src/lib/tones.ts`, shared with the sidebar's per-item `tone` in `src/lib/nav.ts`) so a section has the same color everywhere. Admin pages wrap content in `<SettingsLayout variant="admin">`, which switches the primitives to the larger admin look. Colors are semantic tokens in `src/styles.css` (`bg-card`, `bg-surface`, `text-muted-foreground`, …; dark mode via `.dark`); the public landing uses its own `.lp` token set.

**Integrations** live in `src/lib/<name>/` with `*.server.ts` logic: amoCRM and Bitrix24 sync (leads from them carry `amocrm_id` / `bitrix24_deal_id` and are analytics-only — CRM rules skip them), telephony (`src/lib/telephony/`, one module per provider, all webhooks normalized into `pbx_calls` by `recordPbxCallEvent`), Telegram bot (`telegram.webhook.ts`, one shared bot via `TELEGRAM_BOT_TOKEN`), Gemini for AI (`gemini.server.ts`; call analysis is `analyzeCallById` in `audio-analytics.analyze.ts`).

**Python.**

- `services/ai-worker/` — small FastAPI service (Railway) that drains the AI call-analysis queue with no serverless time limit by calling `/audio-analytics/analyze-one` one call at a time; analysis logic stays in TS. Claims via `amocrm_calls.analysis_started_at` keep it and the pg_cron tick from analysing a call twice.
- `backend-python/` — an older, unfinished FastAPI port of the TS backend (see its `PORT_STATUS.md`). Not in production: `apiFetch` only targets it when `VITE_API_BASE_URL` is set, and it is left empty. The owner decided not to migrate the backend to Python; don't extend this port unless asked.
